# 如何验证系统与模型效果

工程正确性和文案质量分开评估。固定 DEMO 可以验证状态流，但不能当作真实模型质量测试。单元/集成测试通过也不等于已评估所有供应商协议或直播效果。

## 运行测试

```bash
mvn clean verify
```

测试不需要真实模型密钥。当前测试清单以 `src/test/` 和 Maven 报告为准；下面列出持续完善的验证维度，不能把清单本身当作通过记录。

| 维度 | 应验证的失败路径 |
| --- | --- |
| 角色权限 | Reviewer 请求写稿/结束任务时拒绝 |
| 格式校验 | 错字段、超长参数、重复 ID、错误类型不改变数据 |
| 版本一致性 | 并发或过期 patch 被拒绝；旧报告不能批准新稿 |
| 幂等 | 同一工具/外部命令重放不产生重复版本 |
| 覆盖 | 漏读段落、遗漏关系或阻断问题时不能 PASS |
| 取消 | 取消后的迟到模型结果不能写入有效产物 |
| 恢复 | 已接受工具意图重放；不确定模型调用保守暂停 |
| 预算 | Writer、Reviewer 共用预算；耗尽停止而非假成功 |
| 上下文 | 工具调用与结果成对；关键事实和问题不静默丢失 |
| 来源 | DEMO 只能 DEMO_READY，不能伪装真实 MODEL |

## 真实模型协议冒烟

为选定服务使用最低成本的小任务先验证：一次合法工具调用、参数不完整、响应截断、零工具调用、多工具调用、拒答、限流、超时、缺少 usage。保存脱敏的协议行为与配置版本。

先证明模型/API适配器能够跑通工具协议，再评估写作效果。供应商可能对结构化输出、tool_choice、并行工具和 token 字段有不同支持。

## 文案质量评测集

使用虚构且有明确事实边界的任务。每个样本记录事实、约束、参考问题标签和人工审阅标准。例如：

| 样本 | 注入或关注的问题 | 预期行为 |
| --- | --- | --- |
| 收纳盒 | 无依据承重声明 | 指出原句和缺失依据，删除声明 |
| 水杯 | 事实只给500ml，正文写成800ml | 发现数值冲突 |
| 台灯 | 前段承诺介绍调光，后段未兑现 | 发现遗漏承诺 |
| 收纳场景 | 多段反复讲同一卖点仅换词 | 指出信息重复，提出新角度或压缩 |
| 节奏衔接 | “因此”“这种结构”没有前文依据 | 定位相关段落并修订承接 |
| 不足资料 | 用户要求给价格，但资料没有 | 不编造，要求补充或保留明确缺口 |

事实一致和低重复可部分检查，创意、口播自然度与转化效果需要人工判断和业务实验。时长先用文本估计；若要保证成片时长，需要指定声音与语速的 TTS 实测。

## 对照设计

比较三个配置：直接一次生成、单 Writer 加规则检查、Writer 加 Reviewer。使用相同模型、输入、预算上限与任务集合；记录实际消耗，避免双 Agent 只是因为调用更多而显得更好。

人工审阅应尽量隐藏配置来源，并记录：事实错误数、漏检和误报、跨段问题、修复后新引入的问题、重复程度、人工修改时间。另记总调用数、token、时延、无改善修订次数与最终任务状态。

报告至少保留模型/提示词/规则版本、样本数量、标注方法和失败样例。小样本可以说明探索方向，不能支持笼统的“质量提升80%”。

## 24小时扩展前的准入

首版不支持24小时连续任务。扩展前需要实现节目/章节/段落分层任务、批次级恢复、跨批事实与承诺账本、全局覆盖清单、历史索引、预算分配、实测音频时长和跨小时一致性评测。不能仅提高单次输出 token 或去掉段落上限。
