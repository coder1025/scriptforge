# 阅读、演示与讲解路线

## 五分钟演示

先打开工作台，说明当前是固定演示还是实时模型。推荐演示这条可验证的链路：

1. 看输入事实。样例只有折叠、提手与收纳用途，没有承重、销量、价格数据。
2. 看结构计划。每段包含目的、信息增量、承接关系和事实引用。
3. 看首次审稿。初稿故意出现“承重100公斤”，Reviewer 指出没有事实依据，报告定位到原句。
4. 看版本变化。Writer 调用 `patch_script` 替换问题段，其他段落保留；稿件产生新版本。
5. 看复审与交付。旧报告不能批准新稿。新的报告核对当前版本与覆盖范围，宿主最终形成 `DEMO_READY` 或 `READY`。

接着展示某次模型调用的工具参数与真实回执，再看一次上下文检查点。这样访客能把界面行为对应到后端机制。

不要将演示中的预设缺陷称为“真实模型稳定检出率”。真实效果需要另行跑评测；演示用于说明状态、角色和证据如何流转。

## 按问题读源码

建议先运行测试，再从以下目录进入，避免先背提示词：

| 想解释的问题 | 阅读入口 | 自己应当能验证的事实 |
| --- | --- | --- |
| 正文在哪里生成、在哪里保存 | `model/`、`tools/` | 正文进入工具参数，Java 校验后保存正式版本 |
| 两名 Agent 怎样独立 | `runtime/`、`prompts/` | execution、角色权限、上下文与等待状态独立 |
| 重启之后怎么继续 | `store/`、数据库迁移、恢复测试 | 已接受工具意图与未确认模型调用采用不同处理 |
| 为什么旧报告不能提交新稿 | 提交工具、版本和报告测试 | 当前版本与 hash 被宿主校验 |
| 上下文满了怎么办 | `runtime/ContextAssembler.java` | 有输入预算、完整工具对、事实和问题保留 |
| 为什么要多个工具 | `tools/ToolCatalog.java` | 按不同读写/副作用边界设计，而非每个函数暴露一个工具 |
| 模型为什么不能随意操作 | 工具执行校验与 API 访问边界 | JSON 格式、角色权限与业务状态分别约束 |

## 适合讲清楚的四个工程点

**1. 把“模型想做什么”和“系统允许做什么”分开。**

模型可以选择结构、写文本、判断下一步要读哪段资料。它不能决定当前数据库版本、扩大自己的角色权限、取消预算或绕过验收。宿主为调用绑定上下文，并对结果负责。

**2. 审稿作为独立持久执行。**

Writer 发起审稿后处于持久等待状态，Reviewer 从冻结版本开始运行。完成后结果回填到原始工具调用，Writer 可以继续修订。这样既保留工具协议配对，也不用持有数据库事务等待模型。

**3. 动态上下文服务于具体任务。**

稳定指令、精确事实、当前计划和问题必须保留；旧版本全文与重复工具结果不必每轮全部带入。当前段落、前后承接和依赖按需选择。压缩是可追溯的资料整理，不能把丢失事实解释成“模型记住了”。

**4. 验收绑定不可变版本。**

问题被修复意味着正文变了，所以必须重新绑定检查。旧审稿报告是历史证据，不能自动批准新稿。覆盖检查与版本 hash 可以确定性验证，语义正确性还需模型判断与人工评估。

## 面试追问与准备方式

| 追问 | 应回答的重点 | 亲手做一次 |
| --- | --- | --- |
| 为什么不是普通工作流？ | 宿主控制有限状态和权限；角色内部由模型选择工具和修订步骤 | 用真实模型观察不同输入的工具序列 |
| 双 Agent 一定比单 Agent 好吗？ | 未必；存在额外成本、误报和共同盲点 | 同预算单/双角色对照并人工盲评 |
| 中途断电会不会重复执行？ | 依赖持久工具意图和操作幂等；外部模型不确定结果另行暂停 | 在保存工具意图后中断并重启 |
| 为什么不自动重试所有异常？ | 供应商可能已经执行并计费；自动重试有重复成本 | 模拟服务端已接收但客户端超时 |
| 模型说全部通过就能提交吗？ | 不能；版本、hash、覆盖、证据和规则由宿主检查 | 构造旧报告与新稿件不匹配 |
| 上下文压缩后怎么保持事实？ | 精确事实来自冻结输入，原文保存在库中，检查点绑定版本 | 降低预算，检查单位/数字/问题是否保留 |
| 如何保证低重复和创意？ | 只能结合历史检索、检查与评测改善，不能单靠提示词保证 | 人工标注重复、同义改写和重复角度 |
| 能不能直接写24小时？ | 当前限制30分钟/24段；更长任务需要分层任务与跨批检查 | 设计扩展，不冒称当前已支持 |
| 为什么不用某个Agent框架？ | 首版要显式验证业务一致性；框架可替换协议层，但不能代替宿主验收 | 找出引入框架仍必须保留的接口 |
| 是否生产可用？ | 能独立运行和接模型；仍是单工作区、单实例首版 | 按真实任务、失败注入和安全边界做准入 |

## 如何写在简历或仓库介绍里

完成阅读、修改、真实模型实验和验证后，可以这样概括项目本身：

> 基于 Java 21 / Spring Boot 实现脚本创作与独立审稿双 Agent 系统，围绕版本化稿件、持久工具执行、动态上下文和审稿覆盖构建创作—检查—修订闭环；提供可视化执行轨迹、确定性演示和真实模型接入。

个人贡献应写自己真正完成并能解释的部分；AI 辅助实现可以如实说明。不要把未验证的效果、生产用户数、成本降低比例或尚未接入的供应商能力写成既有成绩。能够现场复现一个问题、定位代码并修复，比背诵架构词更有说服力。
